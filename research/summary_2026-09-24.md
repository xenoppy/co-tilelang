# 阶段总结（2026-09-22 至 2026-09-24）

> 截至 2026-09-24 13:00。本文件把目前为止的结果整理成一份可独立阅读的总结，供用户与新会话接手。
> 细节与时间线见 [progress.md](progress.md)；研究内容见 [proposal.md](proposal.md)（v0.3）；计划见 [plan.md](plan.md)（v0.4）；规则见 [rules.md](rules.md)。

## 1. 一句话结论

在本机 RTX PRO 6000 Blackwell（sm_120，188 SM，**600W 功耗墙**）上，两个独立算子共置能比串行快 1.1–1.45×，但**把两者编进同一个 kernel 做 tile 级编排，在最优划分下不比 green context 按 SM 分区更快**。13 个算子对上 D1 的完整主张与弱化主张都是 0/13。理想化合成 kernel 的极限测试表明，这是本卡功耗墙造成的物理上限，而不是我们的设计缺陷：功耗墙起作用时，同 SM 共置最多比分区好 3.5%；功耗墙不起作用时，同 SM 共置能赢 8–28%。

## 2. 研究问题与判定标准（回顾）

- 核心思想（用户确定）：像 Mirage 那样以计算语义描述算子，由编译器把两个算子编进一个 kernel，在 kernel 内以 tile 为粒度编排（放置、顺序、资源划分），并与各自的 tile 实现联合搜索。第一阶段是两个单算子之间的共置。
- 3×2 设计（proposal §4）：实现分三档——solo（各自单跑最优）、lib（从单跑调优库中联合挑选，Rammer / GOLDYLOC 能达到的范围）、derived（按共同资源契约重新推导）；编排分两列——inter（多 stream / green context 分区）、intra（CoKernel）。
- D1（plan §2.8，在看到数据前设定，从未修改）：
  - 完整主张：≥2 对同时满足 T_inter*/T[derived,intra] ≥ 1.10 且 T[lib,intra]/T[derived,intra] ≥ 1.05；
  - 弱化主张：≥2 对满足 T_inter*/T[lib,intra] ≥ 1.10。

## 3. 主要结果

### 3.1 P1：GEMM × GQA decode（5 对，稳态，相对串行）

| 研究对 | T_serial µs | 最好跨 kernel | 最好 CoKernel | T_inter*/T[derived,intra] |
|---|---|---|---|---|
| GEMM 4096³ × decode B16×S8192 | 726.1 | ×1.266 | ×1.252 | 0.989 |
| GEMM 4096³ × B64×S8192 | 1709.4 | ×1.238 | ×1.244 | 1.005 |
| GEMM 4096³ × B32×S8192 | 1060.4 | ×1.446 | ×1.424 | 0.985 |
| GEMM 4096³ × B32×S2048 | 571.4 | ×1.157 | ×1.140 | 0.985 |
| GEMM 2048×4096×4096 × B32×S2048 | 374.0 | ×1.208 | ×1.205 | 0.997 |

- 从 C_lib 挑选相对 solo-best 只值 ≤1.4%，kernel 内外没有差别。
- **唯一有效的 derived 维度是 decode K/V 加载的 L2 evict-first 提示**。在同一轮测量、旋钮完全相同的 31 对变体中，带提示者全部更快（+0.4% 到 +8.7%），每轮能耗低 0.4–8.1%；单跑价值只有 0.1–0.25%。这是一个"只在共置时才值得选"的实现（proposal 效应 4）。但它对 green 分区与 CoKernel 帮助相当，所以与 kernel 内编排无关。
- 其余 derived 维度都更差：split-K −10%、split-KV −1%、每 CTA 更少 head −7%、寄存器上限下的同 SM 共驻 −8%、GEMM A/B evict_last 0 到 −2%。
- 归因：4/5 对受功耗墙约束，所有好的共置方案都在 600W，耗时 ≈ 每轮能耗 / 600W。共置降低能耗靠的是重叠本身（静态功耗只付一次、DRAM 受限的 decode 在更低频率下运行），不同机制之间能耗差 < 2%。r029 受 DRAM 约束，已只比 DRAM 下界慢 4.8%。

### 3.2 P4：causal prefill × GQA decode，与 FlashInfer POD 同条件对比（8 对）

| 研究对 | TL / FI 串行 µs | POD µs（对 FI 串行） | 最好跨 kernel | 最好 CoKernel | POD / 我们最好 |
|---|---|---|---|---|---|
| P2048 × B16×S2048 | 217.5 / 246.4 | 207.4（×1.188） | ×1.284 | ×1.290 | 1.231 |
| P8192 × B64×S8192 | 2870.7 / 3175.5 | 2370.5（×1.340） | ×1.285 | ×1.315 | 1.086 |
| P2048 × B16×S8192 | 469.2 / 501.6 | 378.1（×1.326） | ×1.304 | ×1.308 | 1.054 |
| P2048 × B64×S2048 | 470.0 / 502.5 | 365.1（×1.376） | ×1.308 | ×1.309 | 1.017 |
| 4 个 prefill 为主的次要对 | — | ×1.015–1.100 | ×1.012–1.077 | ×1.037–1.095 | 1.008–1.110 |

- **绝对时间上 POD 在 8 对上都慢于我们最好的方案**（0.8–23%）。按各自串行，POD 在 3/4 个主研究对上高 1.4–5.1%，原因是它的单跑 kernel 更慢（TileLang 串行快 7–12%）。
- 用 POD 的调度策略 + 类似 FlashInfer 的 tile，TileLang 复现 POD 在 0–5% 以内；把 POD 的 decode tile 移植进我们的获胜方案反而更差。
- **同 SM 混跑（CTA 级共驻、POD 式）从未胜过按 SM 分区**：DRAM 受限的两对持平，prefill 为主的对差 6–16%（快的 prefill tile 无法与 decode 共驻；能共驻的小 tile 更慢；混跑 SM 在功耗墙下每轮能耗更高）。
- D1：完整主张 0/8、弱化主张 0/8。

### 3.3 CoKernel 的真正优势：对 SM 划分的鲁棒性

| | CoKernel（SM 级，动态队列 + 接手） | green context 分区 |
|---|---|---|
| 8 个划分中的最差值（P1 / P4） | ×0.999–1.077 / ×1.021–1.128，从不慢于串行 | ×0.590–0.854 / ×0.245–0.766 |
| 按单跑时间成比例划分的 regret（P1） | 1.000–1.092 | 1.097–1.490 |
| 把一个对的最优划分迁移到其他对（P1） | regret ≤ 1.003 | 1.048–1.076 |
| 最优划分下 | P1：green 相等或好 ≤3.9%；P4：CoKernel 在 8 对上都不差于 green，prefill 为主的对好 3–4% | — |

### 3.4 极限测试：理想化合成 kernel（功耗墙是物理上限）

相同总工作量（MMA FLOP + DRAM 字节），稳态，比较"同 SM 共置的最好者"与"分区的最好者"：

| 场景 | 同 SM 最好 / 分区最好 |
|---|---|
| 纯寄存器 MMA × DRAM 流，时长比 0.5 / 1 / 2 | 1.000 / 1.035 / 1.023 |
| 类 GEMM（cp.async + ldmatrix）× DRAM 流，时长比 0.5 / 1 / 2 | 1.001 / 1.007 / 0.993 |
| 94 SM 子设备（功耗不受限） | **1.279** |
| 每 SM 只 2 个 MMA warp（低强度） | **1.118** |
| 类 GEMM，94 SM 子设备 | 1.081 |

- 功耗受限时各方式都在 599–603W，能耗差 0–3.5%，耗时 ≈ 能耗 / 600W。
- **同 warp 交错（步骤级编排的极端形式）在所有场景都是最差的同 SM 方式**：MMA 发射卡在消费流数据的 load 上。
- `setmaxnreg` 在 sm_120a 可用，按角色重分配寄存器有效，但不改变结论。
- 本卡每 SM 的功耗预算约 3.2W（600W / 188）。按公开规格，H100 SXM 约 5.3W，B200 约 6.8W（待核实）。论点在功耗预算更宽的平台上可能成立，需要硬件验证。用户目前拿不到这类硬件。

## 4. 平台与测量方法要点（新会话必须知道）

- **功耗墙是第一约束**：持续 GEMM 负载下频率被压到约 2.1–2.4 GHz（最高 3.09 GHz）；结果必须同时报时间、频率、功耗；时间与 cycles 可能给出相反结论，以时间为准。
- **主测量模式是稳态**（`cobench.bench_steady`：背靠背执行、输入轮换 > 2×L2、温度平稳后开始、各变体交错切片、相对同一次测量中的 serial 计算加速比）。clean-flush 模式（写 2×L2 后 `discard.global.L2`）只用于筛选，它对功耗受限方案高估 8–10%，且在 P4 上排序不可靠（Spearman 0.42–0.71）。
- 踩过并修掉的测量陷阱：只写的 flush 留下脏 L2（访存型 op 慢最多 30%）；时钟探针让所在 SM 保持小 carveout，大 kernel 只剩 187 个 SM（造成"静态持久化慢 20–50%"的假象）；CoKernel 分派槽未对齐让各角色慢 1.5–1.7×；NVML 约 500ms 才刷新；ncu 计数器需要管理员权限（不可用）；不能锁频（无 sudo）。
- **GPU 共享规则**（用户规则 7 + 澄清）：只有别的用户的进程有 SM 活动才算"被占用"，只占显存的不算；被占用时等 30 分钟再查；运行中出现外部活动则做完当前测点后让出；阻塞 > 2h 停下报告。实现在 `cobench.GuardPolicy` 与 `research/bench/scripts/run_guarded.py`。
- 环境：`source research/env.sh`（CUDA 12.9、`~/mpk-env`、kernel 缓存键稳定：`NO_GIT_VERSION=1` + 库与模板头哈希）。

## 7. D1 状态与可选方向（待用户决定）

按 plan §2.8，D1 落在"转向"一侧，除非修订主张。站得住的发现：共置本身的收益与其功耗 / DRAM 来源；CoKernel 的鲁棒性；与伙伴相关的实现（L2 提示）；同 SM 共置在功耗不受限时能赢 8–28%；测量方法上的一系列陷阱。

候选方向（用户于 09-24 表示先考虑，之后在新会话中继续）：

1. **换平台**：在 H100 / B200 等功耗预算更宽的卡上重跑极限测试（合成 kernel 可移植，约 1 小时），若同 SM 共置显著胜过分区，再移植 CoKernel 与 P1 / P4 研究。目前拿不到硬件。
2. **鲁棒 / 自适应共置**：真实 serving 中每步 prefill / decode 比例在变；green 分区需要预测且选错会慢于串行，CoKernel 天然自适应。需要 trace 驱动的端到端评估，与 green + 预测器（Nexus / Bullet 式）及 POD 对比。风险：mKernel、POD 已有运行时自适应的元素。
3. **功耗不受限的场景**：GPU 未被占满、低负载、小 batch 的延迟敏感场景，极限测试显示同 SM 共置能赢 8–28%。需要先确认这类场景的实际重要性。注意：94 SM 子设备的结果是在另一半 SM 空闲时测得，多租户各自忙碌时功耗墙会重新起作用。
4. **子图级 + 能耗视角**（原 P5）：功耗 / 字节主导时，省字节的程序结构（融合、重算）在共置下可能更值钱；最贴近 Mirage 式语义描述，工程量最大。
5. **刻画研究**：把上述发现写成刻画型工作，风险低、贡献偏小。

用户在 09-24 讨论中提出的"像 TileLang 一样在 kernel 内做 tile 步骤级编排（两个算子的联合软件流水）"：极限测试中同 warp 交错最差、分 warp（含 `setmaxnreg`）与 CTA 级共驻在功耗墙下与分区持平，所以**在本卡上**这一方向的上限同样受功耗墙约束；在功耗不受限的平台或场景中值得重新评估。
