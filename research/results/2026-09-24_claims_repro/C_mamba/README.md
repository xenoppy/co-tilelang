# Sub-study C: Mamba-2 chunk-scan / chunk-state (claims C3, C6-mamba)

> 2026-09-24/25. RTX PRO 6000 Blackwell Workstation (sm_120, 188 SMs, 99 KB smem per CTA, 600 W cap).
> Part of `../README.md` (claims C1–C6). The tables in §5 are generated by
> `research/bench/scripts/claims_mamba_report.py` from the JSON files in this directory.

## TL;DR

Ratios are Triton time / TileLang time (> 1 means TileLang is faster), both measured on this card.

The explanations below were each checked by measurement:
- **Chunk-state is DRAM-bound on this card, and both kernels are already near the roofline.** At CT2–CT4
  TileLang moves the compulsory bytes at 1.56–1.60 TB/s (86–89 % of the 1.79 TB/s peak). Triton reaches
  the same 1.58–1.60 TB/s at CT2/CT3, so a 1.6–2.6× speed-up is physically impossible there. CT0/CT1
  (13–26 MB, 12–22 µs) are too small to fill the GPU and are latency-bound for both kernels.
- **Chunk-scan is slower in TileLang because of its default sm_120 lowering.** sm_120 has TMA, so TileLang
  applies its Hopper-style automatic warp specialisation: a TMA producer warpgroup plus one `mma.sync`
  consumer warpgroup. The result is 256 threads with 130–250 registers and 66–82 KB of smem, which fits
  only 1 CTA per SM (CUDA occupancy API). Compiling the same kernel source with the upstream pass config
  `tl.disable_warp_specialized` gives 128 threads, 32–48 KB and 2 CTAs/SM. For the picked configs this
  moves TileLang from 0.77× to 1.01× Triton (CC1), from 0.91× to 1.06× (B8192) and from 1.09× to 1.27×
  (CC4) (§5.6). On H100 the same lowering drives `wgmma`, which sm_120 lacks.
- **The large-shape wins (CC5, CT5, B16384, B32768) come mostly from the baseline's CTA order.**
  mamba-ssm launches `grid = (tiles, batch·chunks, heads)`, so heads vary slowest and the tensors that
  all heads share (cb and C for chunk-scan, B for chunk-state; ngroups = 1) are re-fetched from DRAM once
  per head when they do not stay in L2. The TileLang kernels put heads on the fastest grid axis. Rotating
  only the grid axes of an otherwise unchanged copy of the Triton kernel cuts TileLang's advantage from
  1.66→1.07 (CC5), 1.71→1.07 (B32768) and 2.20→1.49 (CT5).
- **The smem limit shrinks the search space.** 72 of the 90 chunk-scan autotuner configs (every block_M =
  256 config, and every config with more than ~99 KB of pipeline buffers) cannot launch on sm_120. 41 of
  those 72 would fit H100's 227 KB. For chunk-state, 5 of 60 configs cannot launch.
- **This is not a fork effect.** The fork and the upstream v0.1.14 PyPI wheel generate byte-identical CUDA
  source for the picked configs (5 shapes, SHA-256) and run in the same time (±0.4 %).
- **Triton's own autotuner is noisy at CC4.** Its pick changes between processes, and its time there
  ranges from 3.1 to 4.4 ms. Against Triton's best forced config (3.0 ms), TileLang is 1.08× at CC4
  (as-autotuned: 1.09–1.52× across 5 processes).

**Environment:** `~/mpk-env` is unchanged. mamba-ssm 2.2.6.post3's four Triton files are vendored into
`research/bench/baselines/mamba_ssm_triton/`. Throw-away `--target` installs lived in the scratch directory
and were deleted (§9).

## 3. What was run

- **TileLang.**
  - The upstream files are imported by path, unmodified:
    - `examples/linear_attention/example_mamba_chunk_scan.py` (C3 chunk-scan);
    - `examples/linear_attention/example_mamba_chunk_state.py` (C3 chunk-state);
    - `benchmark/mamba2/benchmark_mamba_chunk_scan.py` (C6).
  - The config is picked by each file's own `@autotune`: 90 chunk-scan configs, 60 chunk-state configs,
    `warmup=10, rep=10`. §4 lists what had to be adapted.
  - These files are identical in the fork and in upstream v0.1.14 (`git diff v0.1.14 HEAD` is empty for
    both directories).
- **Triton baseline.**
  - mamba-ssm's `_chunk_scan_fwd` / `_chunk_state_fwd`, called exactly as the TileLang files call them
    (`chunk_scan_triton`, and `chunk_state_triton(..., states_in_fp32=False)`).
  - Triton picks the config with mamba-ssm's own `@triton.autotune` lists, re-tuned in every process. Its
    tuning key does not include batch or seqlen, so every run tunes only one shape per process.
  - One config per kernel (128/256/64, 8 warps) cannot launch on sm_120 (Triton `OutOfResources`: shared
    memory); Triton's autotuner skips it.
  - mamba-ssm 2.2.6.post3 (the version named in `benchmark/mamba2/README.md`) is **vendored**, not
    installed. Only the four pure-Triton files are copied, byte-identical: `ssd_chunk_scan.py`,
    `ssd_chunk_state.py`, `ssd_bmm.py`, `softplus.py` (md5s in
    `research/bench/baselines/mamba_ssm_triton/mamba_ssm/__init__.py`). They sit under the original package
    path, with an `__init__.py` that does not import the CUDA extension.
  - Installing the package instead would have required its CUDA extension or `transformers`
    (`mamba_ssm/__init__.py` imports `selective_scan_cuda` and the model classes).
  - The paper-era mamba-ssm 2.2.4 differs from 2.2.6.post3 in these two kernels only by
    `exp(x) → exp(min(x, 0))` clamps (diffed). With realistic inputs the clamp is inactive (next point).
  - This machine has Triton 3.4.0; the C6 README used 3.5.0. It was not changed (hard rule: no upgrades).
- **Inputs** use realistic Mamba-2 statistics, seed 0, all fp16:
  - dt = softplus(N(0,1) − 2) > 0;
  - A = −exp(N(0, 0.25)) < 0;
  - dA_cumsum = the within-chunk cumsum of dt·A (non-increasing);
  - cb = C Bᵀ per chunk, with B, C ~ N(0, n^-½);
  - x ~ N(0,1), prev_states ~ 0.1·N(0,1), D ~ N(0,1).

  The upstream benchmark feeds `randn` for dt and dA_cumsum instead. With those inputs, mamba-ssm ≥ 2.2.5's
  clamp makes Triton compute a different function than TileLang (timing does not depend on the values;
  correctness does).
- **Correctness**, for every timed kernel at every shape:
  - Each output is compared with the example's own `ref_program`, evaluated in fp32 and sliced over
    batch × 16-chunk blocks.
  - Pass means relative L2 error ≤ 1e-2, no non-finite values, and at most 1 % of elements outside
    atol = rtol = 1e-2 (the examples' tolerances).
  - **All 36 TileLang and Triton outputs pass**, with relative L2 error 2–4·10⁻⁴ and 0 mismatching
    elements (`check` in `bench/<shape>.json`).
  - Every variant in the diagnostics was checked against the output of an already verified kernel
    (Triton or TileLang, same inputs) before it was timed.
- **Timers** (each number in §5 says which one it comes from):
  - **Primary: `cobench.bench_variants({tilelang, triton})`.** Clean L2 flush, host gate, the two kernels
    interleaved, 100 reps, SM clock per rep (ClockProbe) and NVML power. Ratio = median Triton / median
    TileLang.
  - **Graph-mode cross-check for the short kernels** (CC0–CC2, CT0–CT2, B1024): `cobench.bench(mode="graph")`,
    i.e. one CUDA-graph replay of 20–32 back-to-back calls over rotated input copies (> 2× L2 in total,
    so every input is DRAM-cold). TileLang and Triton are alternated for 3 rounds each.
    - This was added because the per-call event times in flush mode are **quantized**: the medians fall
      on a ~2.05 µs grid, e.g. 20.6 / 22.6 / 24.6 µs and 26.6 / 28.6 / 30.6 µs. Sub-study B saw ~4 µs.
      Ratios of kernels below ~60 µs from the primary timer carry this error; for those shapes the
      graph-mode ratio is the one to use.
    - Graph mode runs back-to-back, so larger kernels hit the 600 W cap there (e.g. CC2 and B1024 at
      1.9–2.4 GHz). That is a different regime from flush mode.
  - **Secondary: `tilelang.profiler.do_bench` with defaults**, the examples' own timer (event timer,
    256 MB `zero_()` before each call, mean). It alternates 3× per kernel. For C6 there is also the
    benchmark script's Triton call `do_bench(..., _n_warmup=10, _n_repeat=10)`, and the autotuner's own
    latency (stored in the JSON).
- **Robustness checks.**
  - The autotuner's top-6 TileLang configs were re-timed with the primary protocol ("TL best of top-6").
  - Every mamba-ssm Triton config was forced in turn and re-timed ("best forced Triton",
    `claims_mamba_triton_sweep.py`).
- **GPU policy.**
  - Every GPU step ran as `run_guarded.py -- flock <shared lock> <one script>`, and cobench's own guard
    re-checked pmon for every measurement.
  - All 18 primary measurements record `clean: true` in their guard records (no foreign SM activity in
    the timed window).
  - Waits happened, e.g. 1 h for another user's Ray job (qzr) plus our own sub-studies. The guard counts
    processes of the same user whose pid it cannot resolve any more as foreign, so some waits were
    caused by our own just-finished jobs.

## 4. Adaptations (all in wrappers; no TileLang, example or benchmark file was modified)

1. **Configs above 99 KB of smem.** They compile but fail at launch
   (`Failed to set the allowed dynamic shared memory size to N`).
   - Chunk-scan: **72 of 90** configs fail this way: every block_M = 256 config and every config with more
     than ~99 KB of pipeline buffers. 41 of the 72 would fit H100's 227 KB.
   - 2 more chunk-scan configs (block_M = 256, block_K = 256, 5 stages) do not compile at all: TileLang's
     layout-injectivity check exceeds its 262144-point limit. That is a compiler limit, not specific to
     sm_120.
   - **16 chunk-scan configs remain**, the same set at every shape: M/N/K/stages = 64/32/64/1–5,
     64/32/128/1–2, 64/32/256/1, 64/64/64/1–3, 64/64/128/1, 128/32/64/1–2, 128/32/128/1, 128/64/64/1.
   - Chunk-state: 5 of 60 fail at launch; 55 remain.
   - The upstream autotuner catches these launch failures and skips the configs. For CC0–CC4, CT0 and
     B1024 it therefore ran exactly as shipped.
2. **Autotuner memory leak → config pre-filter.**
   - Every config that fails at launch leaks the input tensors the upstream autotuner just allocated.
   - At CC4 the leak reached 56 GB, and 20 of the failing configs ended in CUDA OOM instead of the smem
     error. The 16 launchable configs had already run, so the CC4 pick is unaffected.
   - For CC5, CT1–CT5 and B2048–B32768 the wrapper therefore removes, before tuning, the configs that
     failed to launch in a reference shape (CC0 for both chunk-scan files, CT0 for chunk-state).
   - A config is removed only when the generated host code shows the same dynamic smem in both shapes.
     That held for every config (`config_filter` in `tune/<shape>.json`).
   - The tuned set is then exactly the set the shipped autotuner would benchmark successfully without the
     leak.
3. **Compile outside the GPU lock.** The autotuner compiles in a thread pool that is GIL-bound here: about
   7 s per config, i.e. 10 min per shape while holding the GPU. `claims_mamba_compile.py` first compiles
   all configs in 16 processes (CPU only), so the autotuner's compile step becomes a kernel-cache hit.
4. **Helion import stub.** `benchmark_mamba_chunk_scan.py` raises ImportError at import time if helion is
   missing. When helion is not installed, the wrapper puts a stub `helion` module into `sys.modules` so
   that the file's TileLang kernel and Triton wrapper can be imported. The helion kernel is never run, and
   the stub raises if called. Helion itself was not measured (§8).
5. **Realistic inputs** instead of `randn` for dt and dA_cumsum (§3).

### 5.3 Clock and power

Values from the primary runs (ClockProbe per rep; NVML board power over the interleaved window, which
includes the ~140 µs low-power flush phases):
- **Small shapes** (CC0, CC1, CT0–CT2): 335–404 W, SM clock 2.69–2.85 GHz for both kernels, no throttle.
- **Large chunk-scan shapes** (CC3–CC5, B4096–B32768): the board sits at the 600 W cap. NVML reports
  `SwPowerCap` in 100 % of the samples at CC3, CC4 and B4096–B16384, in 16 % at CC5, and never at B32768
  (600 W mean all the same).
  - Triton then clocks lower than TileLang: CC3 2065 vs 2647 MHz, B8192 2067 vs 2517 MHz. Its access
    pattern costs more power per cycle.
  - At CC5 and B32768 it is the reverse: Triton 2.75 GHz vs TileLang 2.5 GHz. There Triton is stalled on
    DRAM (the grid-order effect of §6), so its SMs draw less power.
- **Chunk-state large shapes** (CT3–CT5): 559–600 W with little throttling; both kernels at 2.75–2.84 GHz.
- **Temperature**: 54–75 °C throughout.

ahead at the power-capped chunk-scan shapes (CC2–CC4, B1024–B16384: the cycles ratio is 0.08–0.25 lower
than the time ratio), because the cap throttles Triton harder. The verdict changes only at B16384: partly
in time (1.12), Triton ahead in cycles (0.87).

## 6. Why the claims do not reproduce (checked explanations)

### 6.1 Chunk-state CT0–CT4: DRAM-bound, and both kernels are at the roofline

- The roofline table in §5 counts only compulsory traffic (every input read once, the output written
  once).
- **CT2–CT4**: TileLang reaches 1.56–1.60 TB/s, **86–89 % of the 1.79 TB/s DRAM peak**. Triton reaches
  1.58–1.60 TB/s at CT2/CT3. The largest possible speed-up over Triton is therefore about 1/0.88 = 1.13×
  at those shapes, so the claimed 1.65–1.69× cannot happen on this card.
- **CT4**: Triton drops to 1.38–1.41 TB/s (best forced config: 1.41 TB/s), hence TileLang 1.11–1.13×.
  - Rotating Triton's grid does not change CT4 (§6.3), and the 33 MB B tensor fits in L2.
  - The cause of Triton's 12 % loss at CT4 was not isolated further.
- **CT0/CT1** (13 and 26 MB, 12–22 µs; 1024 and 2048 CTAs on 188 SMs):
  - Both kernels reach only 0.9–1.2 TB/s: launch and ramp-up latency dominate.
  - Graph-mode ratios are 0.90 and 0.99.
  - The claimed 2.6× and 2.2× would need Triton to be far from its latency floor on H100. That cannot be
    checked here.
- The TileLang chunk-state kernel itself is fine on sm_120: it reaches 126–131 TFLOPS / 1.54–1.60 TB/s at
  every shape ≥ CT2.

### 6.2 Chunk-scan CC0–CC4 and C6: TileLang's automatic warp specialisation on sm_120

- **What the compiler generates.** Every picked chunk-scan kernel is launched with 256 threads, although
  the source asks for `threads=128`.
  - TileLang turns on its Hopper pipeline because `have_tma(sm_120)` is true
    (`tilelang/cuda/pipeline.py: allow_warp_specialized`).
  - Warpgroup 0 issues TMA loads; warpgroup 1 runs `ldmatrix` + `mma.sync m16n8k16`.
  - `T.no_set_max_nreg()` is set in the example, so no register rebalancing happens.
  - The CUDA occupancy API gives **1 CTA per SM** for every shipped kernel. The limit is registers (at
    237–250 per thread, 256 threads use the whole 64K register file) and/or smem: the warp-specialised
    pipeline allocates 66–82 KB, e.g. 74 KB for 128/64/64/s1 against 48 KB without warp
    specialisation.
- **Controlled experiment** (§5.6, `claims_mamba_diag.py`): the same kernel source, compiled with the
  upstream pass config `tl.disable_warp_specialized`.
  - The kernel then launches with 128 threads, 182–254 registers, 32–48 KB of smem and 2 CTAs/SM (every
    chunk-scan config tested).
  - It is faster at every chunk-scan shape tested: CC1 49–53 → 38.9 µs, B8192 1731 → 1491 µs, CC4
    2836 → 2438 µs.
  - TileLang goes from 0.77–0.80× to 1.01× (CC1), from 0.91× to 1.06× (B8192), and from 1.09× to 1.27×
    (CC4). The Triton times in that run come from the same process.
  - So on this card, TileLang's default lowering costs chunk-scan 15–25 %. Even without it, TileLang only
    reaches parity with Triton at the small and medium shapes; the claimed 1.44–1.96× (H100) is not
    reached.
- **Chunk-state is not affected the same way** (CT1, CT4: no-WS is equal or slower). Its kernel is
  DRAM-bound (§6.1).
- **`tl.disable_tma_lower` had no effect.** The kernels still contained TMA loads. That pass config does
  not turn off the bulk copies used here, so TMA vs `cp.async` could not be isolated.
- **Side finding.** One non-default variant, CC1 config 64/64/128/s1 compiled with
  `tl.disable_warp_specialized`, produced NaN output. It was excluded from timing. The shipped config
  path is correct at every shape.
- **Why this does not show up on H100.** There the same warp-specialised structure drives `wgmma`
  consumers. On sm_120 there is no `wgmma` or `tcgen05` (research/env_versions.md §3.3), and consumers
  fall back to `mma.sync`. The H100 claim itself cannot be re-measured here.
- **Smem and the tile space** (§4): none of the 30 block_M = 256 configs runs (28 fail at launch, 2 at
  compile), and neither do the deeper pipelines of the 128/64/64 tiles. The largest tile that launches is
  128/64/64 with 1 stage, which is the autotuner's pick at 11 of 12 chunk-scan shapes. The kernel reaches 98–102 TFLOPS / 1.0 TB/s at every
  shape ≥ CC2, 56–58 % of DRAM peak and about 20 % of the `mma.sync` peak at the measured clock, so it is
  neither compute- nor DRAM-saturated.

### 6.3 The large-shape wins are mostly the baseline's CTA order (CC5, CT5, B16384, B32768; partly CC4)

- **Evidence.**
  - Triton's bandwidth collapses as shapes grow: 0.72 TB/s at CC4, 0.59 at CC5, 0.70 at CT5, 0.58 at
    B32768.
  - TileLang's stays constant: 1.0 TB/s for chunk-scan, 1.54 TB/s for chunk-state.
  - This happens for every one of Triton's configs (the best forced config is within 0.1 % of the
    autotuned one at CC5, CT5 and B32768).
- **Cause.** mamba-ssm's grid is `(tiles, batch·nchunks, nheads)`, so heads are the slowest axis. With
  ngroups = 1, all heads read the same cb/C (chunk-scan) or B (chunk-state) tile of a (batch, chunk). When
  those tensors are larger than what survives in L2 between two heads, they are fetched from DRAM once
  per head:
  - cb is 268 MB at CC5 and 134 MB at B32768 (plus C);
  - B is 134 MB at CT5.
- **Test** (`claims_mamba_l2diag.py`, table in §5.5). Two plain `@triton.jit` copies of the vendored kernel were launched
  through mamba-ssm's own host function with Triton's picked config:
  - the original `program_id` mapping: same time as shipped (control);
  - axes rotated so that heads vary fastest, the kernel body otherwise untouched.

  Both produce the verified output. With the grid rotated, Triton gets 1.55× faster at CC5, 1.60× at
  B32768 and 1.48× at CT5, and TileLang's advantage drops to **1.07× (CC5), 1.07× (B32768), 1.49× (CT5)**.
  At CC4 the rotation helps a little (1.41 → 1.34); at CT4 not at all.
- **Consequence.** The C6 "reproduced" at seq 32768 and the big CC5/CT5 wins are real for the kernels as
  shipped. They come from a CTA-order choice in the baseline, not from TileLang code generation, and they
  depend on ngroups = 1 (for ngroups = nheads nothing is shared across heads). The H100 figure shows
  TileLang ahead at every shape, including batch 1; on this card that is not the case.

### 6.4 C6 absolute numbers

- TileLang chunk-scan reaches **98–102 TFLOPS** here, against 126–136 TFLOPS on H800.
- Measured against this card's peaks, TileLang runs at about 20 % of the dense 16-bit `mma.sync` peak at
  the measured clock (188 SMs × 1024 FLOP/clk × 2.5–2.66 GHz) and at 56–58 % of the DRAM peak.
- On H800, the README's 136 TFLOPS is 13.7 % of 989 dense TFLOPS, and its compulsory traffic
  (6.996 GB in 5.076 ms at seq 32768) is 1.38 TB/s = 41 % of 3.35 TB/s.
- So TileLang uses this card's DRAM *more* efficiently than it used H800's, and the ratio to Triton is
  what fails to reproduce, for the reasons in §6.2 and §6.3.

    under `cuda-binaries/`).
  - The TileLang autotuner cache gained ≤ 26 MB.
  - `~/.tilelang/cache/torch_extensions` holds 4.4 MB: minference's index op, built by the example.
  - The upstream-wheel check used a separate `TILELANG_CACHE_DIR` in the scratch directory (deleted).

## 11. Files

- `claimed.json`: the claimed ratios (C3 from the vector PDF; C6 from the JPEG) and the paper text.
- `tune/<shape>.json`: the autotuner's pick, per-config latencies, failed configs with reasons, and the
  config filter. `tune/logs/<shape>/autotuner.log` is TileLang's own log.
- `bench/<shape>.json`: the primary result (cobench, with clocks, NVML and guard record), correctness,
  secondary timers, Triton's pick, the top-6 re-timing, and features of the generated source.
- `graphcheck/`, `triton_sweep/`, `diag/`, `l2diag/`, `forkcheck/` (with the generated `.cu` per build):
  the cross-checks and diagnostics of §5–§6.
- `minference/`, `linear_attn/`: the optional parts.
- `logs/`: stdout of every run (compile, tune, bench, diagnostics, guard waits).

## 12. Open issues

- **chunk_size, ngroups and dtype of the C3 figure are not published.** The example defaults (256, 1, fp16)
  are assumed. ngroups matters for §6.3: the baseline's CTA-order penalty exists only because all heads
  share one group.
- **The H100/H800 numbers themselves cannot be re-measured here.** Neither can the Triton versions used
  there: 3.5.0 for C6, unknown for the paper; this machine has 3.4.0.
- **CT4**: Triton is 10–12 % slower than TileLang even with its best config and a rotated grid; the cause was
  not isolated.
- **TMA vs `cp.async`**: `tl.disable_tma_lower` did not remove the TMA loads, so their effect alone was not
  measured (only warp specialisation on/off).
- **TileLang, non-default path**: CC1 config 64/64/128/s1 compiled with `tl.disable_warp_specialized`
  produces NaN output (a TileLang bug candidate). The shipped path is correct.
- **Upstream autotuner leak**: `tilelang/autotuner/tuner.py` leaks each failing config's input tensors
  (56 GB at CC4; OOM for later configs). Worth an upstream issue; worked around here by pre-filtering (§4).
- **cobench guard**: a pmon sample from a process that has already exited has no resolvable owner and is
  counted as foreign. This caused 30-min waits on our own finished jobs (e.g. pids 385161 and 631505 in
  `logs/*`). Suggested fix in `cobench/guard.py`: remember the owner when a pid is first seen.
- **Helion** (C6 third bar) was not measured.
- `.gitignore` has `*.log`: the `logs/` directories and `tune/logs/*/autotuner.log` need `git add -f` if
  they should be committed.
